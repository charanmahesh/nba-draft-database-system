# Database choice

DraftBoard uses PostgreSQL 16 with pgvector as one transactional database. Structured basketball and organizational data have stable entities and relationships: teams, players, performances, memberships, needs and people benefit from typed columns, foreign keys, uniqueness and check constraints. Joins, aggregation, views and window functions support analytics; transactions, triggers and the unique player-season key protect roster and audit integrity even when writes do not originate in the UI.

Scouting reports and generated news contain free text. PostgreSQL stores the original text alongside a 384-dimensional pgvector embedding and model metadata. Cosine search retrieves semantically similar descriptions, while the same SQL statement can join players and enforce position and injury filters. GIN-backed full-text search supplies an interpretable keyword comparison. HNSW makes approximate nearest-neighbour indexing available as the collection grows; at the current small scale the planner can correctly prefer a sequential scan. See [vector-search.md](vector-search.md) for model, indexing, evaluation and limitations.

MongoDB is not needed for this workload: flexible documents do not outweigh the existing relational integrity and joins, and introducing a second datastore would duplicate data and complicate transactions. Neo4j is likewise unnecessary: the implemented relationships are modest-depth joins rather than a graph traversal workload. Neither would replace the need for consistency between structured filters and vector results. This is a scope-based design choice, not a claim that those systems cannot support similar applications. A separate search or graph system could be reconsidered if scale or traversal requirements change, with synchronization and operational costs measured first.
